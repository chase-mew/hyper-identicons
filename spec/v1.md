# Hyper Identicons — Specification v1

Status: **DRAFT — output is not frozen.** Until this document is marked Frozen, the
algorithm and the art set may change, and any given address may render differently
between releases. Do not ship v1 to users who will form an attachment to their avatar
until the status line here says Frozen.

A conforming implementation turns a HyperEVM address into a 32x32 indexed-colour
image. Any two conforming implementations, in any language, MUST produce identical
trait indices and identical pixel output for the same address and the same art set.

---

## 1. Address normalisation

The input is a 20-byte EVM account address.

1. Strip a leading `0x` or `0X` if present.
2. Reject the input unless what remains is exactly 40 hexadecimal characters.
3. Lowercase it.
4. Decode to 20 raw bytes.

Checksum casing (EIP-55) carries no information and MUST NOT affect the output.

## 2. Seeding

```
seed_0 = keccak256(address_bytes)      // 32 bytes
```

Addresses are not uniformly distributed — vanity addresses, `CREATE2` deployments and
contract addresses all cluster in the high or low nibbles. Hashing first removes that
structure. Keccak-256 is chosen because it is the ecosystem's native hash.

### 2.1 Entropy cursor

Trait selection consumes the seed 16 bits at a time, big-endian:

```
next16():
    if offset == 32:                   // current block exhausted
        seed = keccak256(seed)
        offset = 0
    value = (seed[offset] << 8) | seed[offset + 1]
    offset += 2
    return value
```

Re-hashing on exhaustion means the entropy budget is unbounded, so adding layers later
never requires a spec change. It does mean layer order is significant: inserting a
layer shifts every subsequent draw.

## 3. Trait selection

Layers are painted in the fixed order below (later layers paint on top).

| # | Layer       | Purpose                                    |
|---|-------------|--------------------------------------------|
| 0 | `background`| flat fill, plus an optional pattern overlay |
| 1 | `body`      | the cat silhouette                          |
| 2 | `clothing`  | garment across the shoulders                |
| 3 | `mouth`     | mouth below the nose                        |
| 4 | `eyes`      | eye shape and expression                    |
| 5 | `accessory` | eyewear                                     |
| 6 | `headwear`  | hat, worn between the ears                  |

Draws happen in a different order — `body` first, then `background`, then the rest as
above. See §3.2 for why.

For each layer, two draws are made, in this order:

1. **art** — which shape is used
2. **colourway** — which palette that shape resolves against

Splitting shape from colour is what produces a large option space from a small art set.
One body silhouette with eight fur colourways is eight bodies' worth of variety and one
drawing, and it removes the whole class of bugs where a garment drawn for one body
silhouette does not composite correctly onto another.

### 3.1 Weighted choice

Each candidate carries an integer `weight >= 1`. Given candidates with cumulative
weights summing to `W`:

```
pick(candidates):
    target = (next16() * W) >> 16      // multiply-shift, negligible modulo bias
    running = 0
    for each candidate in declaration order:
        running += candidate.weight
        if target < running:
            return candidate
    return last candidate               // unreachable; guards against rounding
```

Candidate order within a layer is significant and is fixed by the art manifest.
Weights are relative, not percentages: a weight of 1 against a total of 200 is a
0.5% trait.

### 3.2 Tone pairing

Every layer except `eyes` declares a `tone` of `deep` or `bright` on each of its
colourways. The two tones are separated by a wide gap in perceptual lightness. The
body's draw is unrestricted, and every other layer follows from it by one rule:
**take the tone opposite whatever the layer is drawn against.**

| Layer | Drawn against | Tone taken |
|---|---|---|
| `body` | — | free |
| `background` | the cat | the opposite of the body's |
| `mouth` | the fur | the opposite of the body's |
| `accessory` | the fur | the opposite of the body's |
| `clothing` | the background | the same as the body's |
| `headwear` | the background | the same as the body's |

A bright cat therefore always stands on a deep field, and a deep cat on a bright one.
Garments are not an exception to the rule: a hoodie or a cap reaches past the cat to
the canvas edge, so the neighbour it has to clear is the field, and being the opposite
of the field puts it back on the cat's own tone.

For eyewear it is the frame slot that flips and the lens that stays dark on either
tone, so a deep cat gets pale-framed shades rather than pale lenses.

`eyes` carry no tone, because each polarity carries itself: a dark eye on a deep cat
is read from its white sclera, and a light sclera on a bright cat is read from its
dark outline.

These are the only dependencies between layers, and they exist because there is no way
around them. Requiring every fur to contrast with every background forces the two sets
into separated lightness intervals, which would mean giving up either dark cats or
light backgrounds. Making the choice conditional keeps both and still guarantees the
contrast.

It is why `body` is drawn before everything else despite being painted second: the
draws that follow need to know what they are dressing. Weights remain relative to the
candidates actually offered, so a colourway's effective rarity on a conditioned layer
is its weight over the total of its own tone, not of the whole layer.

The bands, the thresholds and the measured worst cases are in `AGENTS.md`.
`scripts/audit-colors.ts` prints them and the test suite asserts them.

## 4. Art format

### 4.1 Canvas

48x48 pixels. 32x32 was tried first and could not hold the art style: at that size
the cap logo, the swept sunglasses and the whiskers all collapse into noise. 48
keeps every one of them legible, still encodes the whole trait set in single-digit
kilobytes, and divides evenly into the 24px and 96px sizes address lists render at.

### 4.2 Semantic slots

Art does not store colours. It stores *slots*, resolved to hex at render time by the
layer's chosen colourway. Slot `0` is transparent and is never painted.

| Slot | Char | Meaning                        |
|------|------|--------------------------------|
| 0    | `.`  | transparent                    |
| 1    | `o`  | outline                        |
| 2    | `f`  | fur, base                      |
| 3    | `s`  | fur shadow / whisker line      |
| 4    | `l`  | fur, light (muzzle, chest)     |
| 5    | `p`  | inner ear                      |
| 6    | `a`  | item colour, primary           |
| 7    | `b`  | item colour, secondary         |
| 8    | `c`  | item colour, tertiary / metal  |
| 9    | `w`  | white                          |
| 10   | `k`  | black                          |
| 11   | `h`  | Hyperliquid aquamarine accent  |
| 12   | `g`  | glass / lens                   |
| 13   | `e`  | eye white                      |
| 14   | `i`  | iris                           |

A colourway supplies hex values only for the slots its layer uses. A slot present in
the art but absent from the colourway is a build error, not a runtime fallback.

### 4.3 Encoding

Each art asset is run-length encoded over its tight bounding box:

```
byte 0  top     row of the bounding box  (0..47)
byte 1  left    column of the bounding box (0..47)
byte 2  height  (1..48)
byte 3  width   (1..48)
byte 4+ pairs of (runLength, slot), runLength in 1..255
```

Runs are laid out row-major across the bounding box and MAY span row boundaries. Runs
longer than 255 are split. The pairs MUST decode to exactly `height * width` pixels.
The encoded bytes are published base64.

Storing a tight bounding box rather than the full canvas matters more than it looks:
most assets — eyes, a mouth, a pair of shades — occupy well under a tenth of the
canvas, and the bounding box is what keeps a rich trait set inside a wallet's bundle
budget.

## 5. Rendering

1. Fill all 2304 pixels with the background colourway's `a` colour.
2. For each layer in paint order, decode the chosen art and paint every non-transparent
   pixel over what is already there, resolving slots through that layer's colourway.
3. The result is 2304 hex colours with no transparency.

SVG output emits one `<rect>` per horizontal run of identical colour, on a
`0 0 48 48` viewBox with `shape-rendering="crispEdges"`. Scaling is left to the
`width`/`height` attributes, so a single string serves every display size.

## 6. Detail levels

Two levels are defined. Both use the same seed and the same draws — `mini` simply does
not paint layers 2 through 6.

- **`full`** — all seven layers.
- **`mini`** — layers 0, 1, 4 and 6 (background, body, eyes, headwear).

`mini` exists because a wallet rendering a hundred-row address list gets no value from
whiskers it cannot see, and because the art for the omitted layers is then never
imported and never reaches the bundle. Crucially, an address's `mini` and `full`
renders agree on background, fur, eyes and hat, so the two are recognisably the same
character.

Eyes are in the set despite contributing little at this size. Dropped, the face reads
as blank rather than simplified, which is worse than the bytes are worth.

Because a draw is made for every layer regardless of detail level, `mini` and `full`
can never disagree about a shared layer.

## 7. Versioning

The version namespace is `v1`. Once this document is Frozen:

- No change may alter the output of any address. Not the hash, not the cursor, not the
  layer order, not the weights, not a single pixel of existing art.
- New art may only be added as `v2`, rendered alongside `v1` rather than replacing it.

This is the whole ballgame. A deterministic avatar is an identity, and changing it
later reads to users as deleting their face. `spec/vectors.json` exists to make
violations loud: it pins a set of addresses to their expected trait indices and a hash
of their rendered output, and it MUST be regenerated only when the version namespace
changes.
